# :material-handshake-outline: Bazaar Haggler

**Candidate question:** can a finite, truthful negotiation be reused after domain qualification,
without taking domain judgment or commitment authority?

| Local maturity | Identity | Patterns | Outcome |
| --- | --- | --- | --- |
| **Unaccepted candidate study** | `bazaar.haggler/rev1` | `haggler.open_mandate@1`, `haggler.negotiate@1`, `haggler.close_cod@1` | conversation only |

> Negotiate what was authorized. Invent no leverage. Cross no ceiling. Preserve every refusal.

```text
Scout observation → domain Composition mandate → Bazaar Haggler → domain closure
```

Search, crawl, extraction, saved queries, deduplication, and change observation stay Scout
machinery. Haggler's separate possible office is a durable seller conversation: mandate, thread,
questions, offers, counteroffers, timeout/stop, prepared send, unknown-send reconciliation, and
attributable terms. It can serve distinct domains precisely because it never selects an item,
judges compatibility/suitability, proves identity, sets value or safety policy, holds credentials,
or purchases.

## The closed envelope

`NegotiationMandate@1` pins caller, Pattern/Invocation, principal, intent, expiry, exact listing
observation and thread; material questions and desired evidence; opening offer, item and all-in
ceilings, currency, delivery constraints and concessions; message/follow-up/counteroffer/time/
disclosure/retry caps; truthful template, automation disclosure, prohibited claims and stop
signals; effect consent/standing authority; and a caller-readable outcome schema. It cannot widen
for enthusiasm, private-data barter, invented defects/competitors, refusal, changed item or
payment rail, abuse, expiry, or exhausted caps.

`NegotiationOutcome@1` returns exact terms, attributed claims, requested/received evidence,
contradictions, prepared/send receipts, accepted/rejected offers, stop reason, and uncertainty.
It is never a purchase.

Only after the caller freshly revalidates the candidate, budget, evidence, thread, parcel exposure,
and authority can it issue `CodClosureMandate@1`: one deal, maximum all-in amount, delivery
method, opaque delivery profile, exact disclosed fields/template, expiry, and one send.

## Three scores, divided authority

| Score | Essential path |
| --- | --- |
| `haggler.open_mandate@1` | validate caller/schema → pin listing/thread/terms/caps → separate question, offer and closure authority → required review → commit |
| `haggler.negotiate@1` | load mandate/thread → observe reply through Scout → classify claim/refusal/change → draft one grounded message → validate → authorize/send once → reconcile → await/return/refuse/expire |
| `haggler.close_cod@1` | admit exact closure mandate → revalidate terms/thread/expiry → resolve opaque profile outside Mind → minimum-disclosure payload → authorize/send once → reconcile receipt |

The Mind drafts and classifies. Deterministic tools validate money, caps, phrases, payload fields,
effect identity, and state. The deterministic sender alone resolves an opaque profile after fresh
authority; raw address/phone never enter a prompt. `unknown_send` parks the exact effect and never
automatically resends. The caller creates an expected parcel only after an acknowledged closure.

For [Tech Scavenger](tech-scavenger.md), the sequence is qualified component + mandate → Haggler
outcome → Tech revalidates compatibility/evidence/budget/consent → optional closure mandate → one
closure send → reconciled receipt → Tech creates the parcel. Haggler never changes compatibility,
evidence or price ceilings, budget/reservation, purchase count, parcel, or inspection judgment.

No live fixture proves this candidate. Its first proof is fixture-bound and sendless: a synthetic
RAM listing; available/incomplete/counteroffer/refusal/sold/changed-item/changed-rail/abuse/silence
replies; cap, all-in, stop, and disclosure checks; a simulated lost acknowledgement; and an
accepted term set for a fake Tech consumer.
