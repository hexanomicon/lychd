# :material-access-point-network: 26. A2A

!!! abstract "Context"
    A sovereign node can request bounded labor from another sovereign node. Their identity,
    memory, tools, hardware, and policy remain separate; delay makes the exchange durable
    delegation, never a remote function call.

## Status

**Intercom has a Partial, inert foundation.** Transport-neutral, versioned envelope, verification,
policy, replay, lifecycle, and terminal-adoption contracts exist with a process-local reference
ledger. There is no route, peer registry, discovery, cryptographic implementation, authenticated
durable inbox/outbox, callback handler, transport adapter, Run bridge, or inter-node receipt.
[State](../state-of-the-work.md#a2a-intercom) owns delivery. This law chooses no external A2A
revision: an adapter must pin and test its own version.

## Decision

Intercom will provide versioned asynchronous labor inside Vessel and reuse LychD identity,
persistence, Graph, dispatch, and workers instead of adding a control plane. It exchanges **intents,
not tensors**: no weights, KV cache, Python object, provider client, live toolset, local Sigil,
capability grant, Graph state, or infrastructure command crosses wire. Inputs are bounded values or
immutable ArtifactRefs; outputs are typed values, refs, or explicit non-completion. Receiver decides
whether and how to work on its own iron.

## Peer identity

A peer is cryptographically verifiable network principal, neither Persona nor local Sigil, with
trust record, keys, and authorization. Discovery is untrusted advertisement of versions/endpoints,
public keys, offered task schemas, content/artifact limits, authentication, and optional price or
availability. It grants nothing: each request still needs authenticated lookup, revocation, replay
defence, schema validation, and policy. Personas, private capabilities, topology, and scopes are
not enumerated.

A selected standard may use its well-known discovery path; exact document/path belongs to pinned
adapter, not copied speculation.

## Envelope

Every message names protocol/schema versions; sender and recipient; message/task/idempotency ids;
issued/expiry times; nonce/replay fence; task type; bounded content/refs; and authentication over
canonical envelope. context_id only correlates: continuation additionally needs same peer,
compatible schema, explicit authorization, and unexpired task relation. Unknown field/version,
identity/signature mismatch, expiry, and same id with changed content fail closed.

## Durable task protocol

Admission writes one local peer-task record before work:

```text
RECEIVED → ADMITTED → QUEUED → RUNNING → terminal
```

SUCCEEDED, REFUSED, FAILED, EXPIRED, REVOKED, CANCELLED, and LOST are distinct terminals.
Transport is at-least-once, so inbox admission, claim, adoption, and outbox delivery are
idempotent; repeat same envelope returns same identity, changed-content reuse is a security fault.
Polling, callback, and stream may return results, but none is sole truth. Callback needs exact
egress policy and peer revalidation; silence means neither refusal nor success.

## Graph and Long Sleep

Outbound labor is one opaque station. Only after request and outbox intent commit does Invocation
enter Durable Stasis, release local leases, and await authenticated correlated terminal adoption.
Checkpoint holds peer-task id and local continuation—not foreign state. Expiry, revocation, and
loss take a declared Pattern route; unknown remote effect cannot be silently repeated.

Incoming work is an ordinary local admitted run under peer authority. Dispatcher and Orchestrator
may use their local powers; peer receives no internal handles.

## Sovereignty wall

| Boundary | Question |
| --- | --- |
| Identity | Known, authenticated, current, unrevoked peer? |
| Task | This task and content class authorized? |
| Resources | Local capacity at priority/deadline? |
| Tools | Exact task toolset? |
| Artifacts | Read, retain, return each blob? |
| Egress | Result and callback may leave? |
| Economics | Quote/bounty expressly admitted? |

Security egress law keeps labels/lineage and requires exact peer/callback decision per attempt.
Trust never declassifies. Magus work may outrank peer labor only with peer-visible paused, revoked,
or failed settlement; killing work without a result is forbidden. Resource revocation never widens
tool/data authority.

## Legion and Necropolis

Legion is owned-node delegation: enrollment may narrow shared administration, yet Node Agent retains
identity, fencing, revocation, application authorization, and no Master Sigil/raw host command.
Necropolis is sovereign peerage: foreign Graph, memory, models, and priors stay private. Common
law is labor, not assimilation.

HTTP is first candidate; Nostr/relays remain candidates behind same envelope/inbox/outbox law.
NAT, encryption, and relay signatures require adapter proof. Legion extends one Magus over owned
iron; Necropolis begins at ownership's edge.

## Consequences

!!! success "Accepted"
    - Sovereign execution and local policy survive durable at-least-once exchange.
    - Standard compatibility remains possible without library capture.

!!! failure "Cost"
    - Identity, replay protection, persistence, callbacks, schemas, and reconciliation are security work.
    - Indeterminate outcomes are irreducible until independent interoperability proves the contract.

## Acceptance gates

Intercom needs pinned hostile-envelope fixtures; rotation/revocation/expiry/replay proof; durable
inbox/outbox restart recovery; idempotent admission/adoption; SSRF-safe callback/artifact policy;
Graph park/cancel/timeout/re-entry; peer-visible preemption; and one independent endpoint.
