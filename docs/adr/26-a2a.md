# :material-access-point-network: 26. A2A

!!! abstract "Context"
    A sovereign node can request bounded labor from another sovereign node. Their identity,
    memory, tools, hardware, and policy remain separate; delay makes the exchange durable
    delegation, never a remote function call.

## Status

**Intercom has a Partial, inert foundation.** Transport-neutral, versioned envelope, verification,
policy, replay, lifecycle, and terminal-adoption contracts exist with a process-local reference
ledger. There is no route, peer registry, discovery, cryptographic implementation, authenticated
durable inbox/outbox, callback handler, transport adapter, Run bridge, or inter-node receipt.
[State](../state-of-the-work.md#a2a-intercom) owns delivery. This law chooses no external A2A
revision: an adapter must pin and test its own version.

## Decision

Intercom will provide versioned asynchronous labor inside Vessel and reuse LychD identity,
persistence, Graph, dispatch, and workers instead of adding a control plane. It exchanges **intents,
not tensors**: no weights, KV cache, Python object, provider client, live toolset, local Sigil,
capability grant, Graph state, or infrastructure command crosses wire. Inputs are bounded values or
immutable ArtifactRefs; outputs are typed values, refs, or explicit non-completion. Receiver decides
whether and how to work on its own iron.

An ordinary peer request names an authorized public task schema. The receiver maps that task to its
own exact Scroll and local resolution; the sender neither selects nor learns that decomposition. A
portable Scroll or teaching bundle may cross only as a separately typed, inert artifact. It is not
the receiver's Graph and cannot force local admission, binding, acquisition, or execution.

## Peer identity

A peer is cryptographically verifiable network principal, neither Persona nor local Sigil, with
trust record, keys, and authorization. Public discovery is an untrusted advertisement of exact
protocol/profile versions, endpoints, authentication methods, public task schemas, public
Spell-contract references, content limits, and deliberately coarse price or availability. A claim
means only that the peer advertises it; it proves neither local binding, present availability,
authority, nor admission. An authenticated extended card or query may reveal peer-specific
contracts, ceilings, bounded availability, quote eligibility, or teaching policy.

Discovery never enumerates Personas, Sigils, grants, installed private Scrolls or learned Spells,
local implementation revisions, Graph state, tool/model inventory, backend topology, Tether
coordinates, live queues, artifact bearer URLs, invoices, or payment proofs. A public key repeated
inside an unauthenticated card cannot enroll its own trust.

The first interoperability candidate is the
[A2A 1.0 Agent Card](https://github.com/a2aproject/A2A/blob/main/docs/specification.md) at
`/.well-known/agent-card.json`, plus a versioned LychD extension for exact task and public
Spell-contract metadata. Intentionally public known Spells appear through the card's skill and
extension vocabulary; private catalogue truth does not. The adapter owns document version,
extension URI, authentication, canonicalization, and conformance fixtures; Core does not invent a
parallel `/.well-known/lychd-*` path. Until that adapter is selected and tested, this is protocol
design rather than a shipped discovery claim.

Tether and Veil are transport and ingress layers, not alternative trust models. A conservative
first route is Veil-compiled HTTP exposed only through Tether, then Ward authentication and policy,
then Intercom envelope verification and replay fencing. Public Veil exposure is a later profile.

## Envelope

Every message names protocol/schema versions; sender and recipient; message/task/idempotency ids;
issued/expiry times; nonce/replay fence; task type; bounded content/refs; and authentication over
adapter-pinned canonical bytes. LychD portable artifacts follow
[Workflow serialization](28-workflow.md#portable-declaration); an A2A adapter must separately pin
its envelope profile and signature input. `context_id` only correlates: continuation additionally
needs same peer, compatible schema, explicit authorization, and unexpired task relation. Unknown
field/version, identity/signature mismatch, expiry, and same id with changed content fail closed.

Authentication, revocation, and authorization are rechecked at replay, queue, start, resume,
effect, result egress, and adoption boundaries appropriate to the task. Returning an old
idempotent result cannot treat a now-revoked peer as presently authorized.

## Durable task protocol

Admission writes one local peer-task record before work:

```text
RECEIVED → ADMITTED → QUEUED → RUNNING → terminal
```

SUCCEEDED, REFUSED, FAILED, EXPIRED, REVOKED, CANCELLED, and LOST are distinct terminals.
Transport is at-least-once, so inbox admission, claim, adoption, and outbox delivery are
idempotent; repeat same envelope returns same identity, changed-content reuse is a security fault.
Polling, callback, and stream may return results, but none is sole truth. Callback needs exact
egress policy and peer revalidation; silence means neither refusal nor success.

## Graph and Long Sleep

Outbound labor is one opaque station. Only after request and outbox intent commit does Invocation
enter Durable Stasis, release local leases, and await authenticated correlated terminal adoption.
Checkpoint holds peer-task id and local continuation—not foreign state. Expiry, revocation, and
loss take a declared Pattern route; unknown remote effect cannot be silently repeated.

Incoming work is an ordinary local admitted run under peer authority. Dispatcher and Orchestrator
may use their local powers; peer receives no internal handles.

`remote` is an origin, trust, and authority qualifier—not a fourth service class. A peer may request
foreground, deadline-windowed, or spare-capacity treatment, but receiver policy maps or clamps that
request under peer identity, quotas, local priority, and resource truth. The remote provenance
remains attached whichever tempo is selected.

## Missing Spells and teaching

The receiving policy handles an unknown or incompatible Spell explicitly:

| Policy | Result |
| --- | --- |
| Refuse | Return a bounded incompatibility result naming only the safe public requirement. |
| Request teaching | Ask for an attributed teaching bundle under exact peer, task, size, content, license, and expiry policy. |
| Trusted exact contract | Continue only when the local catalogue admits that exact public Spell contract and an exact local implementation binding. |

A receiver-owned policy configuration selects among these outcomes by exact peer, task/content
class, and Spell identity. A sender may ask to teach, but its request cannot select the policy,
authorize acquisition, or widen the accepted material.

A teaching bundle is a separately identified, size-bounded, content-addressed manifest over
quarantined foreign material, never a live node, package, tool, or registry write. It may contain a
public contract, examples, implementation or artifact references, provenance, license duties, and
claimed evidence. [Assimilation](35-assimilation.md) may turn it into a local candidate;
Spellweaver validates any contract or Scroll candidate while the appropriate Extension, Packaging,
Security, Evolution, and effect owners retain implementation and activation authority.
The original peer task remains refused or otherwise terminal. A successful lesson permits only a
new envelope and new Invocation, so teaching cannot rewrite an in-flight Scroll or inherit its
authority.

Paid work and paid teaching are distinct purchased resources with distinct quote and idempotency
identities. Toll may quote only after task or teaching eligibility; settlement neither
authenticates the peer nor admits work, teaching, publication, or activation.

## Sovereignty wall

| Boundary | Question |
| --- | --- |
| Identity | Known, authenticated, current, unrevoked peer? |
| Task | This task and content class authorized? |
| Resources | Local capacity at priority/deadline? |
| Tools | Exact task toolset? |
| Artifacts | Read, retain, return each blob? |
| Egress | Result and callback may leave? |
| Economics | Quote/bounty expressly admitted? |

Security egress law keeps labels/lineage and requires exact peer/callback decision per attempt.
Trust never declassifies. Magus work may outrank peer labor only with peer-visible paused, revoked,
or failed settlement; killing work without a result is forbidden. Resource revocation never widens
tool/data authority.

## Legion and Necropolis

Legion is owned-node delegation: enrollment may narrow shared administration, yet Node Agent retains
identity, fencing, revocation, application authorization, and no Master Sigil/raw host command.
Necropolis is sovereign peerage: foreign Graph, memory, models, and priors stay private. Common
law is labor, not assimilation.

HTTP is first candidate; Nostr/relays remain candidates behind same envelope/inbox/outbox law.
NAT, encryption, and relay signatures require adapter proof. Legion extends one Magus over owned
iron; Necropolis begins at ownership's edge.

## Consequences

!!! success "Accepted"
    - Sovereign execution and local policy survive durable at-least-once exchange.
    - Standard compatibility remains possible without library capture.

!!! failure "Cost"
    - Identity, replay protection, persistence, callbacks, schemas, and reconciliation are security work.
    - Indeterminate outcomes are irreducible until independent interoperability proves the contract.

## Acceptance gates

Intercom needs pinned hostile-envelope fixtures; rotation/revocation/expiry/replay proof; durable
inbox/outbox restart recovery; idempotent admission/adoption; SSRF-safe callback/artifact policy;
Graph park/cancel/timeout/re-entry; peer-visible preemption; and one independent endpoint.
An adapter that supports Spell compatibility or teaching additionally needs downgrade, unknown-
revision, false-claim, oversized-bundle, provenance/license, quarantine, and no-live-mutation proof.
