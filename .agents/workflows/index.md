# Workflow Playbooks

These tracked playbooks preserve repeatable agent procedure. They own no architecture, delivery
claim, implementation fact, or vocabulary. Load the matching scope selected by
[AGENTS.md](../../AGENTS.md) first; when a playbook and an owner disagree, the owner wins.

| Work | Playbook |
| --- | --- |
| Rewrite or restructure documentation without losing nuance | [Nuance-preserving rewrite](nuance-preserving-rewrite.md) |
| Change tracked source or tests | [File editing](editing/index.md), then one file-type card |
| Hand bounded coding work to an external agent runtime | [Delegated coding](delegated-coding.md) |

## Loading law

1. Load one domain scope.
2. Establish the exact target and its owners.
3. Load one workflow.
4. For file editing, inject one matching file-type card immediately before the first edit when a
   card exists; otherwise remain on the generic editing playbook.
5. Drop cards that no longer match when the task crosses a boundary.

Do not ingest this directory as a handbook. Progressive context is part of the procedure.

## What a playbook must expose

Every workflow names:

- its trigger and acceptance target;
- required inputs and authority probes;
- roles and context boundaries;
- permitted outputs and effects;
- refusal, interruption, and recovery behavior; and
- proportionate verification.

Temporary ledgers and packets may live in an agent's context. Only reviewed artifacts and
maintained receipts enter the repository.
